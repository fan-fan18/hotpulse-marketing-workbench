# 运营效率：定时抓取 / 选题池 / 待审队列 / 批量生成 / 数据看板

这一版解决的是「一个人盯不过来」的问题。链路没变（抓取 → 匹配 → 生成 → 审核 → 发布），
但在链路的每个环节加了能省时间的抓手，并且**所有数字都来自真实数据**，没有写死的演示值。

- 顶部导航从「只有营销工作台」变成四个可切换的视图：**营销工作台 / 商品库 / 内容中心 / 数据看板**（外加「配置后台」）。
- 左侧流程栏只在「营销工作台」里出现；切到其它视图时隐藏，点回去还在原来那一步。

## 一、定时抓取与热点池（服务端）

### 1. 它做了什么

服务端启动 3 秒后先抓一次，之后每 `fetch.intervalMin` 分钟抓一次（默认 10 分钟）。
抓取逻辑与后台「测试全部来源」**共用同一份代码**（`server/sources.js`），不会出现两套实现漂移。

抓取结果不直接塞进配置，而是先进**热点池**：

| 步骤 | 说明 |
| --- | --- |
| 抓取 | 只抓 `enabled=true` 且地址以 http(s) 开头的来源；串行发起，单个来源超时 6 秒 |
| 去重 | 按标题指纹合并（见下） |
| 计热度 | 来源给了真实热度就用真值；没有就按「来源 + 榜单位置 + 被重复抓到的次数」估算（600–990） |
| 采样 | 每次抓取往 `history` 追加一个点，最多保留 24 个点 |
| 清理 | 超过 `fetch.keepDays` 天（默认 7 天）没再出现的条目丢弃；总量超过 300 条按热度截断 |
| 落盘 | `data/news.json`，先写 `.tmp` 再 rename（原子写，写一半断电不会留坏文件） |

### 2. 去重指纹

```
fingerprint('【冷空气来袭】北方多地气温骤降 10℃')
  → '冷空气来袭北方多地气温骤降10℃'
```

去掉括号、标点、空白、大小写差异，取前 60 字。所以「【突发】XX！」和「XX」会被认成同一条，
`seenCount` 累加（工作台卡片上显示"被 N 个来源抓到"），`sources` 里记下所有来源名。

### 3. 趋势

`trendOf(history)` 拿首尾两个采样点算涨幅：≥ +8% 判「上升」，≤ -8% 判「下降」，其余「持平」，
只有一个点就是「新上榜」。工作台的迷你柱状图和「↑ 42%」标签都来自这里。

### 4. 在哪配

后台 →「抓取来源」→「定时抓取与热点池」区块：开关、间隔（1–240 分钟）、保留天数（1–30 天），
并显示服务端当前状态（池内条数 / 今日新增 / 最近一次抓取的耗时 / 下次自动抓取时间）。

关掉开关后服务端不再自动抓，但工作台右上角「一键抓取」仍然可以手动触发。

### 5. 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/news` | 返回 `{ ok, stats, items, runs }` |
| POST | `/api/news/refresh` | 立刻抓一轮，返回 `{ ok, run, stats }`；正在抓时返回 409 |
| GET | `/api/health` | 里也带了 `news` 字段（total / today / up / lastRun / nextRunAt） |

## 二、选题池与内容中心

### 1. 为什么要有

同一条热点被两个运营分别借势，会自己跟自己抢流量。选题池就是给热点排队的地方。

- 入口：Step 1 卡片上的「+ 选题池」，或多选后的「加入选题池」，或 Step 2 简报右上角。
- 状态：**待办 → 进行中 → 已发**，另有「搁置」（搁置不算撞车）。
- 排期：每条选题有一个计划日期，内容中心的月历按日期铺开。
- 撞车：加入时如果 7 天内已有同一条热点（或同一件商品）的选题，会提示"7 天内已有 N 条同热点选题"；
  列表里同一条热点出现多次会标「同热点 ×N」。

### 2. 内容中心（顶部导航 → 内容中心）

- 上排 4 张卡：选题总数 / 待办·进行中 / 本月已排期 / 同热点重复组数。
- 月历：周一开头，6×7 共 42 格，今天高亮，可翻月 / 回到本月；点日历块会跳到列表对应行。
- 选题列表：改计划日期、点「推进」推进状态、点「去工作台」带着这条热点回到工作台、可删除。
- 右侧：状态分布漏斗 + 排期建议。

> 数据存在本机浏览器（`localStorage: hotpulse.workspace.v1`），刷新不丢；换机器不同步。

## 三、待审队列与键盘审核

批量生成出来的文案不会直接覆盖工作台当前稿件，而是统一进**待审队列**（Step 5 右侧第一张卡）。

| 键 | 动作 |
| --- | --- |
| `J` | 下一条待审 |
| `K` | 上一条待审 |
| `A` | 通过（状态改「已通过」，自动跳到下一条） |
| `R` | 打回（弹出原因输入框，**必填**，原因会被记录） |

- 点队列里任意一条，会把它的热点、商品、文案一起载入 Step 5（微博卡片 + 合规校验立刻重算）。
- 只有 `待审` 的条目参与 J/K 翻页；通过/打回后自动跳下一条。
- 快捷键只在「营销工作台 → Step 5」生效，且焦点在输入框里时不触发，不会和打字冲突。
- 在 Step 5 点「通过审核」与按 `A` 是同一条路径，指标只记一次。

## 四、批量生成（多条热点 × 多个风格）

Step 1 勾选多条热点 → 「批量生成」：

- 参与的热点、参与的风格都可勾选（默认全选）；任务数 = 热点数 × 风格数，开跑前直接显示，并给预估耗时。
- **并发数默认 3**（最多 6），不是一次性全发出去。
- 每条任务自动挑该热点匹配度第一的商品；生成后**立刻跑机器校验**，命中可修问题会走自动返工。
- 边跑边填表（热点 / 风格 / 商品 / 机器分 / 结果），有进度条。
- 「停止」只停止**派发新任务**，已经在跑的那几条会跑完再收尾，不会留下半截数据。
- 全部结果进待审队列，失败的条目给出人话原因（比如"热点或创作风格已不存在"）。

## 六、发布后的链接能追踪到什么？（重要）

结论先说：**只靠一条微博链接，能追踪的很有限，而且高度依赖平台是否给你接口权限。**
这一版的做法是「能拿到什么就显示什么，拿不到就说拿不到」，不假装全自动。

| 你能拿到的东西 | 能追踪到什么 | 前提 |
| --- | --- | --- |
| 微博开放平台的 `statuses/show` 或数据 API | 这条微博的**转发 / 评论 / 点赞**等互动量 | 有开放平台应用与对应权限（read 权限、审核通过） |
| 只有链接，没有 API 权限 | **短链点击回流**：自建 `/go/:id` 跳转，记录"有多少人从这条文案点进商品页" | 自建短链域名 + 埋点；需要改发布流程走短链 |
| 什么都没有 | **人工录入**：运营把平台后台的截图/数字填进来 | 纯手工，只能做周报 |

**链接本身拿不到的东西**（别指望）：

- **曝光量 / 阅读量**：微博不通过链接暴露给第三方，除非用开放平台的数据接口。
- **"哪一版文案带来的成交"**：除非每个候选版本带**独立的短链或独立话题**，否则所有版本共用一条商品链接，
  成交只能归因到商品，归因不到文案版本。
- **跨平台统一口径**：微博、小红书、抖音的互动定义都不一样（点赞/收藏/转发/曝光），不能直接相加。

所以要把"效果证明"做成真东西，建议按这个顺序落地：

1. **先做短链**：`/go/:id` → 302 到商品页，同时记一条点击（时间、来源文案 id、UA）。
   这一层不依赖任何平台权限，**是唯一能自己掌控的归因链路**，也是"哪版文案更能带人点"的唯一证据。
2. **再接开放平台**：拿到互动数据后，把「点击 / 互动 / 成交」三段拼起来，才谈得上效果证明。
3. **最后才是 A/B**：同一热点用两个风格各发一条，各带独立短链，跑够样本再比 —— 这正是评测台
   （机器校验 + 模型评审 + 历史对比）在**发布前**做的事，发布后的真实数据是它的补集。

当前版本已经具备的地基：每条队列文案都有独立 id、热点 id、商品 id 与风格名，
接短链时直接用它做 `/go/:id` 的参数即可，不需要改数据结构。

## 七、边界与已知限制

- 选题池、待审队列、生产指标存在**本机浏览器**；换机器/清缓存会丢。要多人协作需把这三块挪到服务端
  （`data/workspace.json` + 接口），数据结构已经按"可序列化"设计。
- 热点池的热度在来源不给真值的情况下是**估算值**，只能用于排序，不能当运营指标对外汇报。
- 定时抓取只在服务端运行；演示模式（双击打开文件）下不会有新条目，也不会伪造。
- 批量生成目前是"每条热点配一件商品"；多商品组合仍走工作台单条生成。
